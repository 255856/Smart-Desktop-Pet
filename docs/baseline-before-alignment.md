## 0. 一句话基线

**A 的对话生硬，根因在代码不在人设；记忆系统"没记住"不是检索算法差，是没有任何检索时机；
工具面数量其实刚好（68），但"清单名字是错的"；
而成本上真正的黑洞不是"token 多"，而是**每轮 8300 个 prompt token 里只有 128 个走了缓存价**
—— 因为 system prompt 末尾挂了一个每轮都变的时间戳。**

## 2. 🔴 成本：缓存被一个时间戳毁掉了（本阶段最重要的发现）

### 2.1 实测数据（真 key，MiniMax-M3，2026-10-28）

**真实对话**（standard 后端，3 轮）：

| 轮次 | prompt tokens | cached | 命中率 |
|---|---|---|---|
| 1 | 1542 | 128 | **8.3%** |
| 2 | 1561 | 808 | 51.8% |
| 3 | 1588 | 128 | **8.1%** |

**用应用真实抓到的请求体（8301 token）重放**：

| 请求体 | prompt | cached | 命中率 |
|---|---|---|---|
| 时间戳**不变**（第 2 次） | 8301 | 8300 | **99.99%** |
| 时间戳**换掉** | 8301 | 128 | **1.54%** |
| **摘掉时间戳**（第 2 次） | 8281 | 8192 | **98.9%** |
| 时间戳**固定**（第 2 次） | 8301 | 8192 | **98.7%** |

**对照实验**（证明 payload 本身完全可缓存）：

| 场景（第 2 次） | prompt | cached | 命中率 |
|---|---|---|---|
| 无 system + 61 个 tools | 10415 | 10414 | **100%** |
| 大 system、无 tools | 1094 | 1093 | **99.9%** |
| 小 system | 197 | 196 | **99.5%** |

### 2.2 修复后（Stage 0 内已实施并实测）

Stage 0 把「每轮变的时间戳与实时状态」从 system message 搬进 **user 消息**（作为独立一条 user 消息，
插在主人本轮发言**前面**；主人原话逐字节不变）；system message 只留稳定内容：
SKILL 手册 / 长期记忆块 / 工具列表。

| | 修前 | 修后（实测 3 轮） |
|---|---|---|
| turn 1 | 128 / 12134 → **1.50%** | 8990 / 9201 → **97.7%** |
| turn 2 | 183 / 12136 → **1.51%** | 8341 / 8477 → **98.4%** |
| turn 3 | 183 / 12120 → **1.51%** | 8368 / 9500 → **70.4%**（这一轮写了记忆 → 记忆块变了 → 块失效一次） |

请求体 diff（两轮同一段对话）：**整份 body 只差 2 行**，都在 user 消息里（时间戳那行）；
system（11678 字符）逐字节相同、tools 61 条相同、主人原话相同。
新增 `tests/test_prompt_cache_stability.py`（10 个用例）钉住「隔一秒重建两次 system prompt 必须字节一致」。

### 2.3 机制与结论

- **MiniMax 按 8192 token 一块缓存**（命中数总是 8192 / 10414 / 11376 这类整数块）。
- A 的 system message 末尾挂着 **`[当前时间:2026-10-28 22:53:04 星期三]`**
  （`hallucination_guard.py:212`）。它落在 system message 的**第 ~700 个 token** 处，
  **每次请求都让第一个 8192 块整体失效** → 只剩 provider 自带的 128 token 底座。
- **代价**：每轮 8301 个 prompt token，只有 128 个走缓存价，**约 8173 个按全价计**。
  修好后每轮约 109 个按全价计 → **约 75 倍**。
- **修法**：把「当前时间」「桌宠实时状态」这类每轮都变的内容**移出 system message**
  （放进 user message 或消息列表末尾），让 system prompt **逐字节稳定**；
  工具 schema / 角色卡 / 行为层这些稳定内容则应尽量多留在 system message 前面。
- **反向结论（重要）**：这**支持** Stage 1 扩提示词 —— 扩的是 system message 里的**稳定内容**，
  在 8192 块命中之后**几乎免费**；扩「每轮都变的内容」才是纯浪费。
  报告 `4.6.3` 那句"先量缓存、再扩提示词"现在有了硬数字支撑。
- **已修**（路线图 **P0-11**），修法与实测见 `2.2`。

| **P0-11 缓存被时间戳毁掉** | 时间 + 实时状态从 system message 搬进 user 消息 | 缓存命中率 **1.5% → 97.7~98.4%**（见 `2.2`） |

**还有一个没修的**：**P0-12 —— standard 路径的 token 漏记**。
台账主键是 `(session_id, request_index, backend, retry)`，但两条路径给 `request_index` 的语义不一样：
`llm_client.py:1106/:1412`（lightweight）**每次 provider 请求**分配（正确），
`langchain_agent.py:1000/:1063`（standard）**每个 astream 分配**（错）。
于是**一个带工具调用的轮次里，standard 后端的多次模型调用共用同一个 index → 只有最后一次被记下，
前面的 token 全丢** —— 工具越多的轮次，成本被低估得越厉害。
（验证需要多次模型调用的轮次，而本机 MiniMax 额度在 2026-10-28 已用尽，见 `8`。）

## 2.5 前缀缓存命中率的稳定性 —— 实测结论（2026-10-29，真 key，MiniMax-M3）

> 这一节回答 PLAN.md「已知遗留问题 1」：**P0-11 的 97.7~98.4%** 和
> **Stage 2.9 重录 20 条的 25.9%** 到底是不是同一个东西？
> 结论：**不是同一个场景，provider 的行为是稳定的、不是 TTL**。

### 2.5.1 测量台

新增 `scripts/measure_cache_hit.py`（可复用）：
走**生产请求路径**（`app/brain/llm_client.py` 的 `LLMClient.chat_stream_events`），
system prompt 用**生产拼装点**（`app/brain/prompt_layer.build_system_prompt`，
与人设 + SKILL + 【记忆规则】+【可用工具列表】+ style guide +【工具解锁】手册
+ 常量段逐字节一致）= **16201 字符 / 7808 token**；
每条请求记 `usage.prompt_tokens`、`usage.prompt_tokens_details.cached_tokens`、
与上一条的墙钟间隔、是否工具调用；台账由 `DESKTOP_PET_TOKEN_LEDGER` 指到临时文件，
**仓库 `data/` 零写入**（实测前后 sha256 逐文件比对一致）。

### 2.5.2 衰减曲线（间隔 0 / 5 / 60 秒，以及「连打 3 条再等 60 秒」）

**A 组 —— 单轮形状**（每条请求都是一条互不相干的新 query，等价于 Stage 2.9 的重录）：

| 间隔 | 请求数 | 真命中（>底座 128） | cached 合计 / prompt 合计 | 命中率 |
|---|---|---|---|---|
| 0 s | 20 | 2（第 14、19 条，各 7822） | 18058 / 157521 | **11.5%** |
| 5 s | 20 | 2（第 7、20 条，7853 / 7808） | 18167 / 157523 | **11.5%** |
| 60 s | 10 | 2（第 1、2 条，7808 / 7853） | 16740 / 78761 | **21.2%** |
| 连打 3 条 + 等 60 s | 9 | 1（第 6 条，7808） | 8832 / 70883 | **12.5%** |

**B 组 —— 多轮形状**（真实对话：历史增长，易变段每轮重新插在最后一条主人原话前）：

| 间隔 | 请求数 | 命中情况 | cached 合计 / prompt 合计 | 命中率 |
|---|---|---|---|---|
| 0 s | 12 | 第 3 条起**每条都命中**（7848→8047 随对话变长） | 79767 / 95924 | **83.2%**（逐条 99.1~99.2%） |
| 5 s | 12 | 第 2 条起每条都命中（7873→8093） | 87927 / 95924 | **91.7%**（逐条 99.2~99.8%） |
| 60 s | 10 | 第 2 条起每条都命中（7873→8048） | 71754 / 79716 | **90.0%**（逐条 99.7~99.9%） |
| 连打 3 条 + 等 60 s | 9 | 第 2 条起每条都命中（7871→8023） | 63702 / 71643 | **88.9%**（逐条 99.7~99.8%） |

> **间隔不是变量**：0 s / 5 s / 60 s / burst 四种节奏下，两组各自的命中率**几乎不变**
> （单轮 11.5~21.2%，多轮 83.2~91.7%）。「TTL / 每分钟窗口 / 每小时窗口」这三条假设
> **全部被数据否掉**。

### 2.5.3 受控对比（同一个 key、同一个模型、同一份 system prompt）

| # | 请求形状 | 请求数 | cached / prompt | 说明 |
|---|---|---|---|---|
| 1 | **整份请求逐字节相同**（无易变段、主人原话也不变） | 6 | 7836×5 / 7837 → **99.99%** | provider 的缓存**完全可靠** |
| 2 | 只有**主人原话**变（system 稳定） | 6 | 1 次 7836，其余 128 → 34.4% | 尾部一变，前缀**不复用** |
| 3 | 只有**易变段**变（主人原话固定） | 6 | 全是 128 → **1.6%** | 同上 |
| 4 | 两者都变（20 条不同 query） | 20 | 2 次 ~7822，其余 128 → **11.5%** | = Stage 2.9 的形状 |
| 5 | 固定前缀消息 + 只有最后一条变 | 8 | 3 次 7808，其余 128 → 38.4% | 偶发前缀复用 |
| 6 | **短 system（207 token）+ 请求逐字节相同** | 3 | 206 / 207 → 99.5% | **没有最小长度门槛** |
| 7 | 短 system（207 token）+ 尾部变 | 6 | 全是 128/183 | 短前缀同样不复用 |
| 8 | **多轮（真实对话形状）** | 8 | 7808→8002 → **99.7%** | 生产真实形状，**可靠** |
| 9 | system 补长到 8985 / 11738 token（尾部变） | 3+3 | 偶发 7936 / 8192 | **前缀长度不是门槛** |

### 2.5.4 结论：provider 到底怎么命中

MiniMax 的缓存**不是**「system 前缀无条件复用」，实测规则是三条：

1. **整份请求逐字节重复** → 整份复用（7836/7837），**稳定可靠**。
2. **请求延续同一段对话**（前面若干条消息与上一条逐字节相同，只是末尾多了新消息）
   → 复用**共享前缀**，命中数**随对话变长而增长**（7848→8047），**稳定可靠**（逐条 ~99.1%）。
3. **请求只与上一条共享 system 一段**（后面整段都换）→ **几乎不复用**，
   只剩 provider 自带的 **128 token 底座**（1.6%）；偶尔（约 5~40%，每次落点不同）
   会命中一次整个 system 前缀（7808~7853）——这是 **provider 侧的落点/路由不确定性**，
   与间隔无关（同一形状连续两次跑，命中落在第 14/19 条 vs 第 7/20 条）。

**所以那两个数字并不矛盾**：
P0-11 的 97.7~98.4% 量的是**真实多轮对话**（规则 2）；
Stage 2.9 的 25.9% 量的是**20 条互不相干的单轮 query**（规则 3，落到 ~11.5%，
那 3 条命中只是运气）。
两者都是真的，**provider 侧没有 TTL、也没有长度门槛**。

### 2.5.5 我方有没有缺陷？—— 没有

- 生产形状（多轮对话）实测 **99.7%**（8/8 命中），与 P0-11 一致，**不需要改代码**。
- 「易变段每轮重插导致位置漂移」看起来像个缺陷，但实测两种形状**逐条命中率一样**
  （生产形状 99.7% vs 易变段留在历史里 99.2~99.3%），**改了也没收益，不改**。
- 真正会吃亏的只有**新开聊天窗口的第一句话**（单轮形状，~11.5%）：
  那一次 system 前缀（7808 token）基本按全价付。
  provider 官方另有 **Anthropic 兼容的「主动缓存」接口**（显式 cache_control 断点，
  见 `platform.minimaxi.com/docs/api-reference/anthropic-api-compatible-cache`），
  **若 OpenAI 兼容端点也认这个字段，就能把单轮形状从 11.5% 拉到 ~99%** ——
  这是唯一还能捞回这块成本的路子，**本次没有验证**（我们只发了标准 OpenAI 形状）。

### 5.2 Stage 2.11：首次运行 / 离线降级（实测，2026-10-29）

> 场景：**一台从没下过模型的机器**。桌宠启动、主人说的第一句话、第一次重建索引
> 会分别经历什么？下面每个数字都是**本机实测**（Windows / Python 3.10.10 /
> torch 2.14.0+cu126 / chromadb 1.5.9），**冷缓存用临时 HF_HOME 模拟**
> （不碰真缓存）。

#### 5.2.1 模型体积与冷下载（临时 HF_HOME 实测）

| 模型 | 角色 | 缓存里实际占用 | 冷下载耗时 | 备注 |
|---|---|---|---|---|
| `BAAI/bge-small-zh-v1.5` | 向量模型（512 维） | **91.9 MB**（96,378,336 B） | **8.3 s**（≈11 MB/s） | config + tokenizer + `model.safetensors` |
| `BAAI/bge-reranker-base` | cross-encoder 重排 | **1081.8 MB**（1,134,374,859 B） | **84.4 s**（≈12.6 MB/s） | 仓库里另有等价的 `pytorch_model.bin`，**不下载**（否则 +1.06 GB） |
| **合计** | | **1173.7 MB**（1,230,753,195 B ≈ 1.15 GiB） | **92.7 s**（连校验共 1m53s） | 落在 HuggingFace 缓存，**不进仓库** |

冷缓存目录里的文件清单与本机真缓存**同构**（逐文件同大小）→ 下载的就是运行时
真正要用的那套文件（不多下一个字节）。

#### 5.2.2 加载耗时（冷缓存 vs 热缓存）

| 场景 | import（torch + sentence-transformers） | 构造模型 | 合计 |
|---|---|---|---|
| 冷缓存（刚下完）第一次加载 · 向量模型 | 14.2 s | 10.0 s | **24.2 s** |
| 冷缓存 第二次加载 · 向量模型 | 12.5 s | 2.2 s | **14.7 s** |
| 冷缓存 第一次加载 · 重排模型 | 12.5 s | 3.8 s | **16.3 s** |
| 冷缓存 第二次加载 · 重排模型 | 12.3 s | 3.4 s | **15.7 s** |
| 本机热缓存 · 向量模型 | 12.4 s | 1.8 s | **14.1 s** |
| 本机热缓存 · 重排模型 | 12.7 s | 3.7 s | **16.4 s** |

**关键结论**：真正的大头是 **import torch + sentence-transformers（≈12.4 s）**，
不是权重本身（1.8~4 s）。所以「模型在不在缓存里」决定的是**要不要多下 1.15 GiB**，
而不是「要不要多等 12 秒」。

#### 5.2.3 首轮聊天延迟（聊天路径里唯一受向量索引影响的那一段）

| 场景 | 首轮召回 | 之后每轮 | 说明 |
|---|---|---|---|
| **全新机器**（没索引、没模型） | **0.014 s** | 0.007 s | 纯字面路径；模型缓存**连碰都没碰**（`embed_state=idle`，没起任何线程） |
| **有索引、模型没下载**（降级） | **2.46 s** | 0.010 s | 那 2.4 s 全在 **Chroma 首次打开 + TF-IDF 拟合**（与模型无关）；召回本身 10 ms |
| **模型在后台加载中**（真实首启） | **2.47 s** | 0.027 s | 模型没就绪 → 走字面路径，**不等** |
| **模型就绪后** | 0.090 s | 0.047~0.064 s | dense 腿 + cross-encoder 重排合计只多花 ≈50 ms |

> 召回 = `MemoryStore.system_block(query)`，也就是每轮聊天注入长期记忆块的那一段；
> LLM 本身的耗时不在表里（它比这一段大两个数量级）。

#### 5.2.4 实测挖出来的两个真 bug（已修）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | **首启随机炸**：语义腿整个死掉（`NotImplementedError: Cannot copy out of meta tensor; no data!`） | `MemoryStore.__init__` 的后台预热**同时**起「向量模型」「重排模型」两个线程，而 transformers 的 meta device 初始化**不是线程安全的** | 模型**构造串行化**（一把进程级锁）：实测修复前 3 轮里 2 轮失败 → 修复后 3/3 通过 |
| 2 | **失败即判死**：模型加载一失败，本进程内**再也不重试** → 桌宠从此「变笨」，除非重启 | 加载错误被记死，没有重试路径 | 失败后冷却 60 s **允许再试一次**（只一次，不是死循环） |

#### 5.2.5 加固后的行为（现在的规矩）

| 场景 | 现在的行为 |
|---|---|
| 模型没下载 | **不下载、不等待**（毫秒级返回）→ 召回退回 substring + TF-IDF |
| 谁来下载 | **显式**跑 `python scripts/prefetch_models.py`（幂等，带进度 + 校验） |
| 想让运行时自己下 | 设 `DESKTOP_PET_VECTOR_ALLOW_DOWNLOAD=1`（**默认关**） |
| 主人怎么知道 | ① 桌宠**冒泡说一声**（项目既有的 say hook 通道）② Windows 系统通知 ③ 面板「健康与维护」显示「向量模型：没下载」+ 该跑哪条命令 ④ 机器可读状态字段 `vector_index_status()["degraded"] / ["notice"]` |
| 聊天路径会不会被索引搞崩 | **不会**：`sync / query / rerank / status` 全部包了 try，异常只变成「降级报告」 |
| 第一次重建索引（模型没下） | **立刻**失败并给出补救命令（不再偷偷下 1.2 GB、也不再干等 180 s） |
| prefetch 之后 | **不用重启**：60 s 内自动重新探测缓存并加载 |
