## 一、已解决

### P1 MiniMax-M3 完全不调工具 ✅

**现象**
主人说「查一下广州天气，提醒我明天带伞」，AgentLoop 连 6 轮都没调成任何工具，
最终回复「唔……主人，刚刚那个操作没能完成，主人再说一遍好不好？~」。
日志里 `tool_choice='required' 服务端接受，但模型仍然没调工具`，连降级 5 次全败。

**根因（实测，非推测）**

MiniMax 官方 API 文档对 `tool_choice` 的合法取值只有 `"auto"` / `"none"` /
**指定具体工具**——`"required"` 不在其中。服务端不报错、直接吞掉。

更糟的是「忽略」不是「无害」：**发了 `tool_choice` 反而大幅拉低命中率**。
用真实输入精确回放（113 条真实聊天历史 + 7 个提醒类工具 + 主人原话，各跑 10~12 次）：

| 策略 | 调工具命中 |
|---|---|
| `tool_choice="required"`（**原第 1 轮用的**） | **1/12** |
| `tool_choice` 指定具体工具（官方文档支持的写法） | 1/12 |
| 完全不带 `tool_choice` | 4/12 |
| 不带 + `LLMClient` 那条干净强制提示 | **9/12** |

即：`required` 约 8%，指定工具名约 8%，不发约 33%，发干净提示约 75%。
旧代码第 1 轮恰好用了命中率最低的那个策略，把最好的那一轮直接作废。

**修复**（`4f4c2aa`）

- `app/brain/llm_client.py`：新增 `_TOOL_CHOICE_SEED` 出厂预置黑名单
  （`minimax-m3`），请求前直接不发 `tool_choice`。
  - 必须做**模型名大小写归一化**：config 里是 `MiniMax-M3`，预置表里是小写，
    不归一化则预置永远命中不了。
  - 运行期学到的名单落盘 `data/tool_choice_unsupported.json`，重启不必再白探测一次。
- `app/brain/agent.py`：`force_tool_use` 从 `turn == 0` 改为**贯穿整个重试阶段**。
  原来第 1 轮强制失败后，第 2~6 轮完全没有强制，只能干看着。
- `app/brain/llm_client.py`：删掉 AgentLoop 自拼的 `[系统提醒] 你刚才只回了文字…`
  伪 user 消息。实测该文案只有 5/12（含内部工具名 + 元叙述，把模型推向道歉式闲聊，
  现场返回过「主人~小汐最喜欢主人了，抱抱亲亲~」），与 `LLMClient` 那条叠加更差（4/12）。

**验证**

- 修复后端到端真实 API 回放 **15 次成功 14 次**（真 `ReminderStore`，非 mock）；
  修复前为 6 轮全挂、0 次成功。
- 埋点确认 payload 中 `tool_choice` 恒为 `None`，每条请求末条均为强制提示。
- 第 3 次回放最有说服力：req0/req1 返回 `reason='stop'` 无工具（旧代码这两轮完全
  无强制），req2 直接成功——正是 force 贯穿全程的改动在起作用。

### P2 get_weather 每次调用都 400 ✅

**现象**
天气工具从来没成功过，一直没人报出来（错误被工具层转成了「工具出错了」）。

**根因**

open-meteo 的 `current` 变量名写成了 `humidity_2m`，正确名是
`relative_humidity_2m`。服务端返回：

```
HTTP 400  Cannot initialize ... from invalid String value humidity_2m
```

**修复**（`4f4c2aa`）— `app/engine/tools/_weather.py` 请求参数与结果取值同步改正。

**验证** 真实调用返回：

```
地点：广州（23.1, 113.2）
当前：晴，33.0°C（体感 35.0°C）  湿度 42%，风速 6.5 km/h
```

### P3 天气播报与实况矛盾 ✅

**现象**
实况明明是晴天，桌宠却播报「广州今天有毛毛雨，31% 的降水概率」。

**根因**
不是「查询时没带日期」——日期一直带着。是 **open-meteo 两个接口对同一天给出矛盾结论**：

```
current : time=2026-10-14T15:15  weather_code=0   → 晴
daily[0]: date=2026-10-14        weather_code=51  → 毛毛雨，降水概率 31%
```

`current` 是当下实况；`daily` 是**全天 24 小时汇总**，凌晨下过毛毛雨就把整天
标成毛毛雨，哪怕此刻大太阳。工具把两行一起吐出，模型采信了 daily 那行。

**修复**（`24692ba`）
当天那行不再报天气现象与降水概率，只保留不矛盾的高低温，并注明
「天气现象以上面『当前』为准」。未来几天不受影响，仍输出完整信息。

```diff
- 2026-10-14: 毛毛雨，24.8~33.2°C，降水概率 31%
+ 今天（2026-10-14）全天 24.8~33.2°C，天气现象以上面「当前」为准（日汇总会把凌晨的天气算进去）
  2026-10-15: 毛毛雨，24.2~32.7°C，降水概率 6%
```

### P4 查天气不查够天数 ✅

**现象**
主人问「提醒我明天带伞」，模型调 `get_weather(days=1)`——只查了今天，
明天的数据压根没拿到，却拿今天的天气作答。

**修复**（`24692ba`）
工具描述与 `days` 参数说明写死：问「明天/后天/周末」时 `days` 必须传够
（明天 2、后天 3），否则查不到那一天。

### P5 天气意图白名单缺 get_weather ✅

**现象**
「查一下广州天气」耗时 **58.9 秒 / 4 个请求**，回复里漏出工具爬取独白：
「让我查广州天气。从最后一次抓取中央气象台的页面拿到了比较完整的预报数据…」

**根因**
两种天气问法都会把内置天气工具排除出白名单：

| 说法 | 命中的意图 | 该意图白名单里有 get_weather 吗 |
|---|---|---|
| 查一下天气 | `query` | ❌ |
| 查一下广州天气 | `web_search` | ❌ |

`query` 的正则 `查(?:一下)?\s*(?:…|天气|…)` 中间夹了城市名「广州」就匹配不上，
于是落到 `web_search`。模型拿不到内置工具，只能 `web_search` + `fetch_url_text`
去爬中央气象台。

**修复**（`d9f5597`）
- 新增独立 `get_weather` 意图（容忍「查…天气」中间夹城市名），排在 `query` 之后、`web_search` 之前。
- 给 `query` / `web_search` / `open_app` 三个白名单都补 `get_weather` 兜底。
- `get_weather` 白名单内保留 `web_search`，供「查火星天气」这类非地球地点退回联网搜。

**验证** 修复后同一句实测走 `get_weather`，超长输入用例由 100.0s 降至 29.4s。

### P6 否定句被当成动作 ⚠️（强制已挡，自选未挡）

**现象**
「不要提醒我任何东西」照样命中「提醒我」意图 → 桌宠去查提醒列表 →
还回「好的，已经帮主人搞定啦~」。主人说的是**别做**，它做完了还报喜。

**根因**
意图正则只匹配动作词，不看前置否定。

**修复**（`d9f5597`）
意图命中位置**之前**的一个小窗口内出现否定词（不要/别/不用/不需要/无需/没必要/
禁止/甭/勿/取消）即跳过。

注意区分方向：否定词在动作词**之后**不算数——
「提醒我别忘了带伞」仍然应判为 `add_reminder`。

**验证** 13 条正反例全部正确：

```
None      <- 不要提醒我任何东西        None      <- 不需要打开任何东西
None      <- 别提醒我了                None      <- 取消刚才的提醒
add_reminder <- 提醒我喝水             add_reminder <- 提醒我别忘了带伞
```

> ⚠️ **只挡住了「强制」，没挡住模型自己选择调工具。**
> `detect_action_intent` 返回 None 只是让 `force_first_turn=False`，工具集照样全量下发，
> 模型仍可能主动调 `list_reminders`。压测中该用例 96.3s、仍被记为过度触发。
> 彻底修需要识别「首个分句被否定」并**整轮撤掉工具**，但「不要打开那个软件，顺便查下天气」
> 这类混合句会误伤，风险需评估后再动。

### P7 HTTP 529 让主人收到空气泡 ✅

**现象**
压测中 `HTTP 529 {"type":"overloaded_error","message":"当前服务集群负载较高"}`，
旧实现直接抛 `LLMError`，主人等了半天收到一个**空气泡**。

**修复**（`d9f5597`）
`app/brain/llm_client.py` 抽出 `_stream_once()`，外层加重试循环：

- 瞬时状态码 `408/409/425/429/500/502/503/504/529` → 最多 3 次，1.5s / 3s 线性退避
- `4xx`（400 参数错 / 401 key 错 / 404 模型名错）→ 不重试，白等
- 重试只包住「还没吐出任何字节」的阶段，不会重放已 yield 的内容

### P8 轮次耗尽 / 全路径无产出时空气泡 ✅

**现象**
压测抓到：「记一下我讨厌香菜，然后提醒我今晚吃饭」跑了 **6 轮、9 次工具调用**
（4×`add_reminder`、2×`delete_reminder`…），最后一条文字都没产出。
间歇性复现，非必然。

**根因**
原有两条兜底各有前提：
- 兜底一要求 `executed_tools` 非空
- 兜底二要求 `over_sanitized` 为真

两条都不成立时就什么都不发。

**修复**（`e294495`）补一条**无条件**兜底。最窄的缝（既没调工具也没吐内容）
也必须给一句诚实的「我没说完」。

**原则** 让主人面对空气泡是最伤的 UX 失败模式，宁可多一句也不许空。

### P9 多步任务只做一半 ✅

**现象**
「查一下广州天气，提醒我明天带伞」——模型调完 `get_weather` 就转头做总结，
提醒那一半被静默吞掉，主人只看到一条天气播报。

**为什么判据是数量而不是工具名**
最初试过「意图对应的工具调了没有」，**被实测否决并回退**：意图名不等于实际会用的
工具名——「帮我搜一下十月新番，并打开B站」意图判成 `open_app`，模型实际调的是
`web_search` + `open_website`，按名字比对就成了「一件都没做」，白刷 3 轮重试。

**修复**（`d9f5597`）
新增 `count_request_actions()` 做纯语言分句计数；要求 N 件事而实际只执行 M 件时，
给**一次**纠正机会（硬限 1 次，避免白刷）。

```python
「查一下广州天气，提醒我明天带伞」 → 2
「帮我搜一下十月新番，并打开B站」 → 2
「今天天气怎么样」               → 0（没有动作动词）
```

**验证**
L3 层（多步组合，8 条 × 2 次）通过率 **62% → 81%**。剩余 3 条失败**全部是压测台
拦截 `open_website` 造成的假失败**——模型如实报告「工具被压测拦截了」「地图连试了
好几个都打不开，主人要不要换个网站」，这正是期望中的行为。真实失败清零。

现场复现可见 P13 的闸门在起作用：连调 4 次 `open_website` 后模型自己换成了
`open_app` / `list_installed_apps`，不再无限循环。

### P10 单次请求延迟过长 ❌（根因不可解，体验已覆盖）

**实测数据**（同一批语料）

| 用例 | 修复前 | 修复后 | 单请求耗时拆解 |
|---|---|---|---|
| 超长输入 | 100.0s | 29.4s | — |
| 查一下广州天气 | 58.9s | 47.1s | `[41.9, 3.2]` |
| 搜一下最近的AI新闻 | 66.7s | 60.4s | `[43.4, 1.9, 5.6]` |
| 不要提醒我任何东西 | — | 96.3s | `[47.8, 48.4]` |
| 帮我搜一下原神最新版本 | — | 59.9s | `[39.4, 4.6, 3.3]` |

**结论**
慢在**单个请求**而非重试循环——这是 MiniMax-M3 推理模型自身的延迟，
**代码层改不动**。

**体验侧其实已经覆盖**
原本担心「主人对着空白屏幕干等 40 秒」，核对后发现
`chat_window._typing_dots_html()` 的**三点跳动动画**从占位气泡插入那一刻就在跑
（`_refresh_streaming_message` → `meta = "typing…"`），整个等待期都有视觉反馈。
所以**不需要**再造一套「还在想」的提示，那是重复投资。

**若仍要优化，只剩两个方向**
- 首个 token 的超时阈值 + 超时后降级为非推理模式
- 评估 `extra_body={"reasoning_split": True}`，思考与正文分离以缩短首字延迟

### P11 工具独白 / 内部清单泄漏给用户 ✅

**现象**
`_STYLE_RULE` 明令禁止工具名与内部推理出现在给主人的文本里，但清洗规则拦不住。
压测抓到三类实况：

```
要查火星天气。1. 工具都成功执行了
2. 主人要求：查火星天气 - 我已经搜到了相关数据
3. 数据来源确认：

让我查广州天气。从最后一次抓取中央气象台的页面拿到了比较完整的预报数据：…

1. get_weather（成功）：广州 晴 33度
2. add_reminder（成功）：已设置提醒
请给主人最终答复
```

**根因**
`sanitize_text` 的 `_strip_meta_by_sentence` 是**逐句**判污染，盖不住
「编号 + 内部词」和「工具名（成功）」这两种**行级**形态。

**修复**（`ea9a184`）
新增 `_strip_internal_checklist()` 做行级 + 句级清理：
- 行首是序号且行内出现内部过程词（工具都执行 / 数据来源 / 主人要求 / 逐条对照…）→ 整行删
- 行首是 `工具名（成功|失败|已取消）` → 整行删
- 无序号的爬取叙述 → 句级删

**关键：句级词表必须收窄**
行级宽表里有「我查」「我搜」，而**「我查到的天气是晴」是对主人能说的话**，
按宽表删会把正文清成空气泡——那比泄漏更糟。句级只收
「抓取/爬取页面」「调用 schema」「给主人最终答复」这类**动作来源**描述。

**验证** 6 条泄漏样本全清 + **6 条正常回复零误删**（含「第一步带伞，第二步关窗」
这类主人自己的分步说明）。

### P12 web_search 缺降级后端 ✅（装了但中文网络下未必可用）

**现象**
`requirements.txt` 里 `ddgs>=9.0.0` 被**注释掉**，DuckDuckGo 降级后端永不生效。
Tavily 一旦失败（限流/网络/欠费），`web_search` 直接不可用，且 Tavily 的失败信息
被吃掉后才轮到这里，报的是「未安装 ddgs」，主人只看到一句搜索失败。

> 排查提醒：Tavily key 配在 `config.yaml` 的 **`brain:` 段**下而非 `llm:` 段下。
> 曾因读错段位误判为「应用没传 key」——应用本身是对的（`brain_controller.py` 有传）。

**修复**（`ea9a184`）
取消注释 `ddgs>=9.0.0`，并装进项目自己的 `.local-packages`
（`start.bat` 已把它加进 PYTHONPATH）。

**⚠️ 重要限制：装了不等于能用**
实测 `ddgs` 底层请求打的是 `https://www.google.com/wml/search`，在中文网络环境下
**必然超时**。也就是说这个降级后端在当前使用场景下形同虚设。

**若要真正兜底**，应换一个国内可达的免 key 源（如 Bing/搜狗的 HTML 端点），
或干脆在设置页暴露「搜索后端」开关并如实告知可用性，而不是默默失败。

### P13 同一工具反复重试 ✅

**现象**
模型对同一个失败的工具连续重试 6 次（`open_website` ×6），每次只换参数，
既白等又占满轮次，最后还是失败。

**修复**（`ea9a184`）
`app/brain/agent.py` 新增按工具名的失败计数（跨轮次）：

- 连续失败 `_MAX_SAME_TOOL_FAIL = 2` 次后，本轮对话内不再提供该工具
- 闸门命中时明确告诉模型：「改用别的工具，或直接如实告诉主人这一步做不到、为什么」
- 成功的工具清零；**只数「工具自己说没成」**，主人取消 / 确认超时不算

**验证** `tests/test_narration_and_retry.py` 两条用例：
连调被切在 2 次、健康工具不被牵连；回退闸门后测试确实变红。
压测现场可见模型在 4 次失败后自行换成了别的工具。

## 三、压测方法

### 语料分层

`tests/stress_corpus.py`，54 条，分四层，每层期望行为不同，
这样命中率能反推问题出在哪一层：

| 层 | 条数 | 期望 | 测什么 |
|---|---|---|---|
| **L1 闲聊** | 10 | 不该碰工具 | 过度触发 |
| **L2 单步工具** | 10 | 恰好调 1 个 | 漏触发 / 错路由 |
| **L3 多步组合** | 8 | 调 ≥2 个 | 只做一半（P9） |
| **L4 边界** | 14 | 不崩、不乱来 | 空输入 / 超长 / 歧义 / 否定 / 危险指令 |

L4 含危险指令（锁屏、关机、删除文件），压测台在 registry 层拦截，**只记录不执行**。

### 运行

```bash
python tests/stress_run.py                    # 全量
python tests/stress_run.py L3                 # 只跑某层
python tests/stress_run.py L3 --reps 3        # 每条 3 次看稳定性
python tests/stress_run.py --out report.json  # 落明细
```

输出按层给出通过率、中位/最慢耗时、问题类型分布。

### 结果对比

同一条语料、同一 API 条件，统一判据后：

| 层 | 修复前 | 修复后 |
|---|---|---|
| L1 闲聊 | 90% | **100%** |
| L2 单步工具 | 70% | **100%** |
| L3 多步组合 | 62% | **81%** |
| L4 边界 | 64% | **79%** |
| **合计** | **30/42 = 71%** | **36/42 = 86%** |

> 上表为第一轮修复（P1~P8 + P9 的分句计数）后的结果。
> 后续 P11~P13 修完后单独重跑 L3 层（8 条 × 2 次）：**62% → 81%**，
> 且剩余 3 条失败**全部是压测台拦截 `open_website` 造成的假失败**——
> 模型如实报告「工具被压测拦截了」「地图连试了好几个都打不开，主人要不要换个网站」，
> 这正是期望中的行为。

> 修复后剩余 6 条失败里，**3 条是压测台拦截 `open_app`/`open_website` 造成的假失败**
> ——模型如实报告「被压测拦截了」，这其实是对的。

### 压测台自身的三处判据缺陷（已修，值得记取）

1. `PARTIAL` 按「不同工具名去重」计数 → 「查上海天气，同时查北京天气」调两次
   `get_weather` 是两件事，按去重只算 1 个，误报。改按调用次数。
2. `DANGER_EXECUTED` 把只读工具也算危险执行 → 「把电脑锁屏」调 `system_info`、
   「删除桌面文件」先列文件再劝阻主人，两条都是**正确**行为，全被误报。
3. 三条期望本身写反了：「提醒我」模型反问才是对的；提醒列表为空时不该硬删。

## 五、经验教训

### 1. 先量再改，不要凭直觉猜

本轮最关键的一次转折：我最初猜是 `max_tokens=1024` 太小（推理 token 吃光预算），
实测 1024 时照样返回 `tool_calls`——假设被推翻。
真正的原因只有在**真实 API 上跑对照实验**才能发现，而且结论与直觉相反：
不是「被忽略」，是「主动有害」。

### 2. 官方文档的参数取值表比记忆可靠

`tool_choice="required"` 在 OpenAI 生态里是常识，但在 MiniMax 官方文档里
根本不是合法取值。服务端不报错这件事极具迷惑性——它让「参数没生效」
看起来像「模型不听话」。

### 3. 意图名 ≠ 实际会用的工具名

两次尝试都栽在这上面（「意图对应的工具调了没有」被否决）。
凡是靠**名字**对齐意图与行为的方案，先找反例；靠**数量/分句**这类
与具体工具无关的信号要稳得多。

### 4. 压测台自己的 bug 会伪装成被测代码的 bug

「危险工具被执行」听起来像安全事故，实际是我的分类器把只读工具算成了危险执行。
压测结论在下结论前必须逐条回看原始输出。

### 5. 期望写错比实现写错更隐蔽

六条失败里有四条是语料期望写反了（模型的行为其实是对的）。
写压测语料时要先想清楚「什么行为才算错」，不能只想「我期望它做什么」。

### 6. 空气泡是最伤的 UX 失败模式

任何路径、任何异常、任何清洗结果，最终都不允许「一条文字都不给」。
